Homelab Rack Simulator — Workspace Redesign

A visual proposal for restructuring the main workspace shell. The goal: return screen space to the rack canvas, end the navigation confusion between workspaces and view modes, and make rack health glanceable. No data-model or feature changes — this is a re-organization of what already exists.

1 · The current design, as observed

Captured live from the running app (18U rack, 14 devices, 18 cables, light theme). Five structural problems are visible in a single screen.

Current main workspace — live capture, 1690×910 viewport.
P1 · Three rows of chrome
Title bar, stats/filter bar, and Create/Actions/File bar stack ~150px of UI above the canvas before any rack is visible. The rack — the product — gets what is left over.
P2 · 12+ controls in one toolbar
View modes (2D/3D/Cables), lenses (Port Labels/Topology/Gallery), tools (Cable Planner), actions (Add inter-rack cable), view flip (Front/Rear), and settings (Search/Dark) all sit in one undifferentiated row. Nothing says what is global vs canvas-level.
P3 · Two navigation systems collide
The left rail offers workspaces (Build Rack / Check Health / Run Ops…); the toolbar offers view modes (2D / 3D / Cables). "Build" (workspace) vs "2D" (view) is a distinction users must discover by trial and error — they are two different axes rendered as competing peers.
P4 · Rack contents rendered twice
The U-by-U device list next to the rack repeats exactly what the rack already shows spatially — two representations of the same data competing for the same attention, doubling the width the canvas needs.
P5 · Inspector is an endless stack
Properties, 18 cable routes, Port Reservations, Port Speed/Media and the Plugin Manager are piled into one scroll column. Admin concerns (plugins) sit inside a working panel, and the cable list pushes device properties off screen.
P6 · Stats read like debug output
"19″ front·U 17/18·14 devices·18 cables" is a log line, not a health readout. Capacity, power, weight and heat — the four things a rack planner actually watches — have no thresholds and no visual status.
P7 · Zoom controls in three places
A floating panel (100%, zoom-in, search), a separate Pan button, and a "44" badge in the toolbar above — three partial controls for one mental operation, one of them floating on top of the canvas content.

1
One top bar, not three rows of chrome
Brand, workspace switcher, global search (⌘K), theme and settings merge into a single 52px bar. The stats row and the Create/Actions/File row leave the chrome — actions move into the canvas header's overflow menu.
Why better: ~150px of vertical space returns to the rack. One scan line for "where am I" instead of three.
2
Workspaces become one segmented control
Build / Check / Ops / Plan / Fleet is the only top-level navigation — a single segmented control in the bar. The duplicate left-rail workspace buttons disappear; the rail keeps tool shortcuts only.
Why better: ends the P3 collision. Workspace = which job; view mode = how I look at it. Each axis now has exactly one home.
3
Icon rail for tools, library slides over
The rail shrinks to 52px of icon shortcuts (library, cables, reports, outline). The device library opens as a slide-over panel on the canvas and closes after a drag — it is a picker, not permanent furniture.
Why better: reclaims ~260px of horizontal space for the rack 95% of the time; the library is full-width only while picking.
4
Rack health strip replaces the debug string
Capacity, Power, Weight and Heat become four chips with mini-bars and green/amber/red status dots, sitting in the canvas header next to the layout name. Values come from the existing validation.ts rack totals — no new computation.
Why better: the four numbers a rack planner watches are glanceable at threshold, not decoded from "19″ front·U 17/18·14 devices…".
5
View modes scoped to the canvas
2D / 3D / Cables and Front / Rear live at the top-right of the canvas header — the thing they actually mutate. Lenses (Port Labels, Topology) and tools (Cable Planner) go into a canvas overflow menu.
Why better: controls sit next to their effect (proximity principle). The global bar stops carrying canvas-local state.
6
The duplicate U-list is gone
The rack is the list — click a device to select it. For keyboard and screen-reader users the same list survives as an optional "Outline" rail tab, not permanent pixels.
Why better: one representation of rack contents instead of two; the canvas nearly doubles its effective width.
7
Inspector gets single-context tabs
Properties / Cables / Ports tabs with counts replace the endless stack — one context visible at a time, badges preserve awareness of the others. Plugin Manager moves out of the inspector entirely, into ⚙ Settings.
Why better: the inspector answers "the thing I selected" instead of being a second app. No more scrolling past 18 cable routes to rename a device.
8
One zoom cluster, bottom-right, map-style
＋ / － / fit in one corner cluster, plus scroll-to-zoom and drag-to-pan as primary input. The floating panel, the Pan toggle and the toolbar zoom badge all collapse into this.
Why better: one control for one mental operation, in the corner every map/canvas app has trained users to look.
9
Category accents and honest shelves
Every device block carries a 3px category accent (network blue, compute violet, storage orange, power green, patch cyan). Shelves render as dashed, hatched, italic — visually "not equipment". Selection is a glow ring, not a 1px outline.
Why better: rack composition is readable at a glance — you can spot "all network gear up top, power at the bottom" without reading a single label.

3 · Why this design is better — change by change

Each change maps a observed problem to a concrete re-organization and the UX principle behind it.

Before (observed)After (proposed)Principle
Three stacked chrome rows (~150px) before any rack pixels. Single 52px top bar; canvas header carries layout name + health + view modes. Content over chrome — maximize pixels for the primary object.
Workspaces (rail) and view modes (toolbar) compete as peers; "Build" vs "2D" learned by trial. Two axes, two homes: workspaces in the bar, view modes on the canvas. One control per conceptual axis; mode errors (Norman) eliminated.
12+ toolbar controls at equal weight: views, lenses, tools, actions, settings. Bar holds 3 global things (workspaces, search, settings); everything canvas-local moves to the canvas. Hick's law — fewer, grouped choices decide faster; proximity couples control with effect.
Stats as a punctuation-delimited debug string, no thresholds. Four health chips with bars + status dots from existing validation totals. Glanceability — status perceived pre-attentively (color/shape), not read.
Rack contents rendered twice: visual rack + adjacent U-by-U list. Rack is the single representation; U-list demoted to an optional Outline tab (a11y preserved). Single source of truth per screen; redundancy splits attention.
Inspector = infinite stack of Properties + 18 routes + reservations + speed + Plugin Manager. Tabbed inspector (Properties / Cables / Ports) with count badges; admin moved to Settings. Progressive disclosure — one context at a time, badges retain ambient awareness.
Zoom in three places: floating panel, Pan toggle, toolbar badge. One bottom-right cluster + scroll/drag gestures. Convention (every map/canvas tool) + one control per operation.
Devices and shelves look identical; selection is a hairline outline. Category color accents, hatched shelf style, glow-ring selection. Pre-attentive attributes carry category; selection must be unmistakable.

Implementation note: this proposal re-arranges existing components only. The health strip consumes src/utils/validation.ts rack totals; the tabbed inspector re-slices PropertyPanel.tsx and cable panels; the slide-over library reuses ComponentLibrary.tsx; the segmented workspace control re-skins the existing workspace switcher from App.tsx. No store, routing, or data-model changes are required. Estimated scope: App shell + 3 component wrappers, behind one layout feature flag.

4 · Cables view redesign

Same shell as section 2 — only the canvas column and inspector change. The current cable map is visually strong, but everything around it fights it.

Current Cables view — live capture.
PC1 · Filters hidden behind "+5 more"
Cable-type filters are chips that overflow into a "+5 more" — the filter you need (e.g. power) is the one that got hidden.
PC2 · Inspector shows device properties, not the cable
In a cable view, the right panel still edits the selected device's name and weight. Cable context — endpoints, length, type — is buried in a collapsed list under Properties.
PC3 · "Dim others" vs "Hide others"
Two adjacent toggles for one mental operation (focus on some cables). The difference is only discoverable by clicking both.
PC4 · Length health is invisible
The app knows each route's length and the standard cable-length table, but mismatches surface only after exporting a BOM — not where you route.
PC5 · View toggle wraps and uneven
"2D map / 3D routing / Table" renders as uneven two-line pills next to a giant "18 routes" block — the primary mode switch of this view looks like an afterthought.

C1
Type filter rail — nothing hidden
Every cable type gets a permanent row: color swatch, count, and a solo (◉) eye. The "+5 more" overflow disappears; the filter you need is always visible.
Why better: recognition over recall — and one click solos a type instead of chip-hunting.
C2
Cable-first inspector
Selecting a cable replaces the device form with a cable card: From device/port → To device/port, routed vs recommended length, slack note, and route actions. Device editing stays one click away in 2D.
Why better: the inspector answers the question this view exists for — "where does this cable go and is its length sane".
C3
One highlight behavior, no toggle pair
Hover or select any route — in the map, the rail, or the list — and the rest auto-dim (as shown by the faded tray lines). "Dim others" / "Hide others" collapse into this single, predictable behavior.
Why better: one mental operation, one mechanism; no mode discovery by clicking both toggles.
C4
Length health where you route
Routes whose length deviates from STANDARD_CABLE_LENGTHS_MM get an amber ⚠ marker on the map and a badge in the inspector — the data already exists in routing.ts / validation.recommendCableLength().
Why better: problems surface at the point of decision, not after a BOM export.
C5
BOM summary in the header
Routes, total meters, and warning count as chips next to the layout name; Export BOM lives here too instead of inside a collapsed inspector section.
Why better: procurement-facing numbers are ambient, and export is one click from the view that produces it.
C6
Map / 3D routing / Table as one clean control
The sub-view switch becomes a single segmented control in the canvas header — equal-width pills, no wrapping, no giant "18 routes" block competing with it.
Why better: the primary mode switch of the view finally looks like one.

4b · The 3D routing mode — the wiring reference for the build

Same capture technique: the real scene from the current app with the proposed UI composited on top. If the device 3D is the build reference, 3D routing is its wiring counterpart — which tray a cable takes, where it drops, how much slack it keeps. Today it is a dark, uncontrollable corner; the redesign gives it the same rail, the same inspector and the same camera language as every other view.

Current Cables → 3D routing mode — live capture.
PR1 · Small, dark, uncontrollable scene
No camera presets, no zoom control, no way to isolate one cable. Thin runs on a ghosted rack — you squint and orbit blindly.
PR2 · "Clean / Realistic" is a cryptic pair
The one control that changes what the scene means — idealized tray runs vs slack-and-sag realism — is two unexplained text buttons.
PR3 · Inspector still edits the device
Same failure as the 2D map: in a view that exists to inspect cables, the right panel edits the selected device's name and mount side.
PR4 · Filters and highlight don't carry over
The "+5 more" chips and the Dim/Hide toggle pair belong to the 2D map; the 3D mode inherits the same problems instead of shared solutions.

R1
One mode switch, one header
Map / 3D routing / Table is the same segmented control with the same BOM summary as the 2D map. 3D routing is a mode of the cables view — not a separate page with its own furniture.
Why better: switching modes changes the visualization, never the layout around it.
R2
Routing style becomes a real control
Clean vs Realistic moves to the header as a labeled Style switch: Clean = idealized tray runs for planning; Realistic = slack, sag and service loops for verifying the physical build.
Why better: the control that changes what the scene means is finally labeled — you always know which truth you are looking at.
R3
Same camera language as the device 3D
The Front / Rear / ISO / Top + auto-rotate dock from section 5 appears here unchanged. One set of camera habits covers both 3D scenes (and the cable layer from D6).
Why better: learned once, used everywhere — no per-scene orbit guesswork.
R4
Hover a cable, know the cable
Hovering floats type, endpoints and length; clicking selects. The ghosted devices already tell you this view is about cables — identification completes the sentence.
Why better: thin colored lines become named routes without a single blind click.
R5
Cable-first inspector, plus Follow route
The same cable card as the 2D map (endpoints, length vs recommended), with two actions: Follow route — SmoothCameraRig flies the camera along the path — and Focus in map for jumping back to the 2D context.
Why better: the inspector answers the same question in both modes, and Follow route is the build-verification move a 2D map cannot offer.
R6
One rail, synced across modes
The type filter rail — including solo — is shared view state: solo "structured" here and the 2D map shows the same subset when you switch back.
Why better: filters are a property of what you're looking for, not of which mode you're in.

5 · 3D view redesign — a build reference, not a gimmick

The 3D view is the spatial truth of the rack: how the build will actually look once assembled, how devices organize by depth, what collides with what — things the 2D view structurally cannot show. It is a reference you build and compare against, not a demo. The current shell treats it as look-only "inspection"; the redesign makes it a first-class working view with real controls, real data, and a path to act on what you see.

Current 3D view — live capture.
P3D1 · No camera controls
OrbitControls are hidden knowledge — drag, scroll, right-drag. "Front view" is a label, not a button. There is no way back to a canonical angle except guessing.
P3D2 · The depth promise is not kept
The subtitle says "compare device depth" but no depth readout exists anywhere in the view — you rotate and eyeball it.
P3D3 · No labels, no hover info
Dark slabs in a dark rack. Without clicking, you cannot tell the NAS from the UPS — faceplate textures only resolve at close zoom.
P3D4 · Loading and recovery are invisible
The 3D chunk is lazy-loaded (~860KB) and WebGL recovery exists in code, but the user sees neither a loading state nor a recovery notice.
P3D5 · Devices and cables live on separate islands
The 3D device view shows no cables; 3D cable routing is a different mode buried inside the Cables view. You can never see the rack the way it will actually be — devices and their wiring together.
P3D6 · Framed as look-but-don't-touch
The view is labeled "3D inspection". For a builder using the render as their assembly reference, there is no path to act on what they see — no labels to identify gear, no depth readout, no clean view to hold against the physical rack.

The scene above is the app's real 3D render, captured live from the current build — the proposed UI is composited on top, so you are judging the design on the actual rack, not a redrawn approximation.

D1
Camera preset dock
Front / Rear / ISO / Top plus auto-rotate, bottom-center. SmoothCameraRig already animates transitions — the presets just give it buttons. OrbitControls stay as the free-look fallback.
Why better: hidden gestures become discoverable controls; "get me back to front" is one click, not a guessing drag.
D2
Hover tooltips + labels toggle
Hovering a device floats its name, U-span, depth and watts; the Labels toggle pins them for all devices. Identification no longer requires clicking blind.
Why better: identification precedes selection — you can find the NAS without opening three wrong inspectors first.
D3
Depth-check card makes the promise real
The inspector gains a depth card: device depth plotted against the rack's railMinDepthMm–railMaxDepthMm band, with rear clearance computed. Data already in the layout model, previously unexposed.
Why better: depth organization is exactly what 2D cannot show — the card makes it numeric, so you organize by millimetre instead of by eyeball.
D4
Loading and recovery made visible
A skeleton + progress chip while the lazy 3D chunk loads, and a toast when CanvasWithRecovery rebuilds the scene after a context loss. The mechanisms exist; they were just silent.
Why better: a 860KB lazy chunk and GPU recovery without UI feedback reads as "broken" — status makes it read as "working".
D5
Same shell, same health strip, plus a perf escape hatch
The canvas header carries the same health chips as 2D/Cables, so status is identical across views. A perf mode (in the overflow) drops port-level geometry and labels on weak GPUs.
Why better: one shell everywhere means zero relearning per view; perf mode keeps big layouts usable on integrated graphics.
D6
Cable layer — devices and routes in one spatial view
The Cables toggle overlays routed paths (CableViewer3D splines) on the device scene, merging the two existing 3D islands into one. You see the UPS, the NAS and the actual cable slack between them — the rack as it will physically be.
Why better: wiring is half of "how it will look"; hiding it in a separate mode made the 3D view lie by omission.
D7
Work from the 3D view — and hold it against the physical rack
Selection, the tabbed inspector and move actions behave identically in 3D, so organizing (nudge a device a U, re-check the depth card) happens where the spatial consequence is visible. Photo mode strips all chrome for a clean render you can compare against the real rack during assembly.
Why better: the view graduates from "inspection" to the builder's reference — organize in it, then verify the physical build against it.
