设计提案 · v1 · 2026 年 8 月

Homelab 机架模拟器 — 工作区重新设计

这是一份关于重构主工作区框架的视觉提案。目标是：把屏幕空间还给机架画布，终结工作区与视图模式之间的导航混乱，并让机架健康状况一目了然。不涉及任何数据模型或功能变更——这只是对现有内容的重新组织。

→ Read the English version (英文版)

1 · 当前设计实况

截取自正在运行的应用（18U 机架、14 台设备、18 条线缆、浅色主题）。单个屏幕中就能看到五个结构性问题。

当前主工作区 — 实时截图，视口 1690×910。
P1 · 三行界面框架
标题栏、统计/筛选栏和 Create/Actions/File 栏在画布上方叠了约 150px 的界面，之后才能看到机架。机架——也就是产品本身——只能分到剩下的空间。
P2 · 一个工具栏塞进 12+ 个控件
视图模式（2D/3D/线缆）、透镜（端口标签/拓扑/图库）、工具（线缆规划器）、操作（添加机架间线缆）、视图翻转（正面/背面）和设置（搜索/深色模式）全都挤在同一行里，毫无区分。没有任何迹象表明哪些是全局的、哪些是画布级的。
P3 · 两套导航系统互相冲突
左侧栏提供工作区（Build Rack / Check Health / Run Ops…）；工具栏提供视图模式（2D / 3D / 线缆）。“构建”（工作区）与“2D”（视图）的区别只能靠用户试错去摸索——它们本是两个不同的维度，却被渲染成了互相竞争的同级入口。
P4 · 机架内容被渲染了两次
机架旁边逐 U 排列的设备列表，与机架本身的空间化呈现完全重复——同一数据的两种表现形式争夺着同样的注意力，还让画布所需的宽度翻了一倍。
P5 · 检查器面板是一条无尽的堆叠
属性、18 条线缆路由、端口预留、端口速率/介质和插件管理器全堆在同一个滚动列里。管理类事项（插件）混在一个工作面板中，而线缆列表把设备属性挤出了屏幕。
P6 · 统计信息读起来像调试输出
“19″ 正面·U 17/18·14 台设备·18 条线缆”是一行日志，而不是健康状况读数。容量、功率、重量和热量——机架规划者真正盯着的四项指标——既没有阈值，也没有可视化的状态。
P7 · 缩放控件分散在三处
一个浮动面板（100%、放大、搜索）、一个单独的平移按钮，以及上方工具栏里的“44”徽标——同一个心智操作被拆成三个残缺的控件，其中一个还浮在画布内容之上。

1
一条顶栏，而不是三行界面框架
品牌、工作区切换器、全局搜索（⌘K）、主题和设置合并进一条 52px 的栏。统计行和 Create/Actions/File 行移出框架——操作项搬进画布头部的溢出菜单。
为何更优：约 150px 的垂直空间还给机架。“我在哪”只需扫一眼，而不是扫三行。
2
工作区合并为一个分段控件
构建 / 检查 / 运维 / 规划 / 集群是唯一的顶层导航——顶栏中的一个分段控件。左侧栏里重复的工作区按钮消失，侧栏只保留工具快捷方式。
为何更优：终结 P3 的冲突。工作区 = 干什么活；视图模式 = 怎么看待它。每个维度现在都有且只有一个归属。
3
图标栏放工具，组件库改为滑出面板
侧栏收缩为 52px 的图标快捷方式（组件库、线缆、报告、大纲）。设备组件库以滑出面板的形式覆盖在画布上打开，拖入后即关闭——它是一个选择器，不是常驻家具。
为何更优：95% 的时间里为机架回收约 260px 的横向空间；组件库只在挑选设备时才占满宽度。
4
健康状态条取代调试字符串
容量、功率、重量和热量变成四个带迷你进度条和绿/黄/红状态圆点的芯片，放在画布头部、布局名称旁边。数值来自现有 validation.ts 的机架汇总——无需新增计算。
为何更优：机架规划者盯着的四个数字在触及阈值时一目了然，而不用从“19″ 正面·U 17/18·14 台设备…”里解码。
5
视图模式收归画布
2D / 3D / 线缆和正面 / 背面放在画布头部右上角——也就是它们实际影响的对象旁边。透镜（端口标签、拓扑）和工具（线缆规划器）收进画布溢出菜单。
为何更优：控件与其作用对象相邻（邻近性原则）。全局栏不再背负画布局部的状态。
6
重复的 U 列表取消
机架本身就是列表——点击设备即可选中。对键盘和屏幕阅读器用户，同样的列表以可选的“大纲”侧栏标签页形式保留，而非常驻像素。
为何更优：机架内容只剩一种表现形式；画布的有效宽度几乎翻倍。
7
检查器面板改为单上下文标签页
属性 / 线缆 / 端口标签页（带计数徽标）取代无尽的堆叠——一次只显示一个上下文，徽标保持对其他上下文的感知。插件管理器彻底移出检查器面板，归入 ⚙ 设置。
为何更优：检查器面板回答的是“我选中的这个东西”，而不是变成第二个应用。改个设备名再也不用滚过 18 条线缆路由。
8
一个缩放控件组，右下角，地图风格
＋ / － / 适应窗口集中在一个角落控件组，滚轮缩放和拖拽平移作为主要输入方式。浮动面板、平移开关和工具栏缩放徽标全部并入其中。
为何更优：一个心智操作对应一个控件，位置就在每个地图/画布类应用都训练用户去看的那个角落。
9
类别色条与诚实的托板
每个设备块带一条 3px 的类别色条（网络蓝、计算紫、存储橙、电力绿、配线青）。托板以虚线、斜纹、斜体渲染——视觉上明确表示“这不是设备”。选中态是一圈发光环，而不是 1px 细线。
为何更优：机架构成一眼可读——不用读任何标签就能看出“网络设备都在上方，电力设备在底部”。

3 · 为什么这个设计更好 — 逐项对比

每一项改动都把一个已观察到的问题映射到具体的重组方案及其背后的 UX 原则。

改前（现状）改后（提案）原则
看到任何机架像素之前，先叠三行界面框架（约 150px）。 单条 52px 顶栏；画布头部承载布局名称 + 健康状况 + 视图模式。 内容优先于框架——把像素最大化地留给核心对象。
工作区（侧栏）与视图模式（工具栏）作为同级入口互相竞争；“构建”与“2D”的区别靠试错习得。 两个维度，两个归属：工作区在顶栏，视图模式在画布上。 每个概念维度对应一个控件；模式错误（Norman）被消除。
12+ 个工具栏控件权重相同：视图、透镜、工具、操作、设置。 顶栏只放 3 个全局项（工作区、搜索、设置）；所有画布局部的内容移到画布上。 席克定律——更少且分组的选项决策更快；邻近性把控件与效果关联起来。
统计信息是一串标点分隔的调试字符串，没有阈值。 四个健康芯片，带进度条 + 状态圆点，数据来自现有的校验汇总。 可瞥读性——状态通过前注意加工（颜色/形状）被感知，而不是被阅读。
机架内容渲染两次：可视化机架 + 旁边逐 U 的列表。 机架是唯一的表现形式；U 列表降级为可选的大纲标签页（保留无障碍支持）。 每屏一个信息源；冗余会分散注意力。
检查器面板 = 属性 + 18 条路由 + 预留 + 速率 + 插件管理器的无限堆叠。 标签页式检查器面板（属性 / 线缆 / 端口）带计数徽标；管理功能移到设置。 渐进式披露——一次一个上下文，徽标保留环境感知。
缩放分散在三处：浮动面板、平移开关、工具栏徽标。 一个右下角控件组 + 滚轮/拖拽手势。 遵循惯例（所有地图/画布工具皆如此）+ 一个操作一个控件。
设备与托板外观毫无区分；选中态是一根发丝级细线。 类别色条、斜纹托板样式、发光环选中态。 前注意属性承载类别信息；选中态必须 unmistakable（绝不会认错）。

实现说明：本提案只重新排布现有组件。健康状态条消费 src/utils/validation.ts 的机架汇总；标签页式检查器面板是对 PropertyPanel.tsx 和线缆面板的重新切片；滑出式组件库复用 ComponentLibrary.tsx；分段工作区控件是对 App.tsx 中现有工作区切换器的重新包装。无需改动 store、路由或数据模型。预估范围：应用外壳 + 3 个组件包装层，置于一个布局特性开关之后。

4 · 线缆视图重新设计

外壳与第 2 节相同——只有画布列和检查器面板发生变化。当前的布线图本身视觉上很强，但它周围的一切都在与它作对。

当前线缆视图 — 实时截图。
PC1 · 筛选器被藏进“+5 更多”
线缆类型筛选器是一排芯片，溢出后折叠成“+5 更多”——你需要的那个筛选器（比如电源）恰恰是被藏起来的那个。
PC2 · 检查器面板显示的是设备属性，而不是线缆
在线缆视图里，右侧面板编辑的仍是所选设备的名称和重量。线缆的上下文——端点、长度、类型——被埋在属性下方一个折叠列表里。
PC3 · “调暗其他”对“隐藏其他”
同一个心智操作（聚焦某些线缆）却有两个相邻的开关。它们的区别只有把两个都点一遍才能发现。
PC4 · 长度健康状况不可见
应用知道每条路由的长度和标准线缆长度表，但不匹配的问题只有在导出 BOM 之后才会浮现——而不是在你布线的地方。
PC5 · 视图切换换行且参差不齐
“2D 布线图 / 3D 路由 / 表格”渲染成宽窄不一的两行药丸按钮，旁边还杵着一个巨大的“18 条路由”块——这个视图最主要的模式开关看起来像事后补上去的。

C1
类型筛选栏——不再隐藏任何项
每种线缆类型都有一个常驻行：色块、数量和单显（◉）眼睛图标。“+5 更多”的溢出折叠消失；你需要的筛选器永远可见。
为何更优：识别优于回忆——而且一键即可单显某种类型，不用再在一堆芯片里翻找。
C2
线缆优先的检查器面板
选中一条线缆后，设备表单被替换为线缆卡片：起点设备/端口 → 终点设备/端口、实际与建议长度、松弛量说明和路由操作。设备编辑在 2D 视图中仍一点即达。
为何更优：检查器面板回答的正是这个视图存在的意义——“这条线缆连到哪里，长度是否合理”。
C3
一种高亮行为，不再有成对开关
悬停或选中任意一条路由——在布线图、筛选栏或列表中——其余线缆自动调暗（如图中变淡的线槽线所示）。“调暗其他”/“隐藏其他”合并为这单一、可预期的行为。
为何更优：一个心智操作，一种机制；不再靠把两个开关都点一遍来摸索模式。
C4
长度健康状况就在布线之处
长度偏离 STANDARD_CABLE_LENGTHS_MM 的路由会在布线图上获得琥珀色 ⚠ 标记，并在检查器面板中显示徽标——数据已经存在于 routing.ts / validation.recommendCableLength()。
为何更优：问题在决策点上浮现，而不是等到导出 BOM 之后。
C5
BOM 摘要进入头部
路由数、总米数和警告数以芯片形式放在布局名称旁；导出 BOM 也放在这里，而不是藏在检查器面板的折叠区块里。
为何更优：面向采购的数字随时可见，且从产生这些数据的视图一键即可导出。
C6
布线图 / 3D 路由 / 表格合并为一个干净的控件
子视图切换变成画布头部的一个分段控件——等宽药丸，不换行，也没有巨大的“18 条路由”块与它抢位置。
为何更优：这个视图最主要的模式开关终于有个模式开关的样子了。

4b · 3D 路由模式 — 搭建时的走线参照

同样的截取手法：取自当前应用的真实场景，叠加拟议的界面元素。如果说设备 3D 是搭建参照，那么 3D 路由就是它的走线对照——每根线走哪个线槽、在哪里下垂、留多少余量。如今它是一个又暗又无法操控的角落；重新设计让它拥有与其他视图相同的筛选栏、相同的检查器面板和相同的相机语言。

当前的 线缆 → 3D 路由 模式 — 实时截取。
PR1 · 场景又小又暗、无法操控
没有相机预设，没有缩放控件，无法单独隔离一根线缆。幽灵化的机架上是细细的线条——你只能眯着眼盲目地转。
PR2 ·「整洁 / 真实」是一对看不懂的按钮
唯一能改变场景含义的控件——理想化的线槽走线 vs 带余量与下垂的真实模拟——只是两个没有说明的文字按钮。
PR3 · 检查器仍在编辑设备
与 2D 布线图同样的失败：一个为查看线缆而生的视图，右侧面板却在编辑所选设备的名称和安装面。
PR4 · 筛选与高亮没有延续过来
「+5 more」折叠 chips 和「调暗/隐藏」开关对属于 2D 布线图；3D 模式继承了同样的问题，而不是共享的解决方案。

上图场景取自应用真实的 3D 线缆路由渲染（实时截取），拟议的界面元素叠加其上。

R1
一个模式开关，一个头部
布线图 / 3D 路由 / 表格是与 2D 布线图相同分段控件，配相同的 BOM 摘要。3D 路由是线缆视图的一种模式——而不是另起炉灶、自带一套家具的页面。
为何更优：切换模式只改变可视化方式，周围的布局纹丝不动。
R2
走线样式成为真正的控件
整洁 / 真实移入头部，成为带标签的「样式」开关：整洁＝理想化线槽走线，用于规划；真实＝余量、下垂与检修环，用于核对实体搭建。
为何更优：改变场景含义的控件终于有了标签——你始终知道自己看的是哪一种真相。
R3
与设备 3D 相同的相机语言
第 5 节的 正面 / 背面 / ISO / 顶部 + 自动旋转停靠栏原样出现在这里。一套相机习惯覆盖两个 3D 场景（以及 D6 的线缆图层）。
为何更优：学一次，处处可用——不必在每个场景里盲目摸索旋转手势。
R4
悬停一根线，读懂一根线
悬停即浮出类型、端点和长度；点击即选中。幽灵化的设备已经告诉你这个视图的主角是线缆——可识别性补完了这句话。
为何更优：彩色细线变成有名有姓的路由，不再需要盲目点击。
R5
线缆优先的检查器，外加沿线漫游
与 2D 布线图相同的线缆卡片（端点、实际 vs 建议长度），配两个动作：沿线漫游——SmoothCameraRig 驱动相机沿路径飞行——和在布线图定位，一键跳回 2D 上下文。
为何更优：检查器在两种模式下回答同一个问题，而沿线漫游是 2D 布线图给不出的搭建核对动作。
R6
一个筛选栏，跨模式同步
类型筛选栏（含单显）是共享的视图状态：在这里单显「结构化布线」，切回 2D 布线图时看到的是同一个子集。
为何更优：筛选取决于你在找什么，而不是你身处哪个模式。

5 · 3D 视图重新设计 — 是搭建参照，不是噱头

3D 视图是机架的空间真相：组装完成后实际的样子、设备按深度如何排布、什么和什么会碰撞——这些都是 2D 视图在结构上无法呈现的。它是一份供你搭建并对照比对的参照，而不是演示品。当前的外壳把它当作只能看的“检视”；重新设计让它成为一等的工作视图——有真实的控件、真实的数据，以及一条对所看见的内容采取行动的路径。

当前 3D 视图 — 实时截图。
P3D1 · 没有相机控件
OrbitControls 属于隐藏知识——拖拽、滚轮、右键拖拽。“正面视图”是个标签，不是按钮。想回到标准角度只能靠猜。
P3D2 · 深度对比的承诺没有兑现
副标题写着“对比设备深度”，但整个视图里不存在任何深度读数——你只能旋转着用眼睛估。
P3D3 · 没有标签，没有悬停信息
深色机架里的深色板块。不点上去，你根本分不清 NAS 和 UPS——面板贴图只有放大到很近才看得清。
P3D4 · 加载与恢复过程不可见
3D 代码块是懒加载的（约 860KB），WebGL 恢复机制在代码里也存在，但用户既看不到加载状态，也看不到恢复提示。
P3D5 · 设备与线缆住在两座孤岛上
3D 设备视图不显示线缆；3D 线缆路由是埋在线缆视图里的另一个模式。你永远无法看到机架实际将成为的样子——设备和它们的走线在一起。
P3D6 · 被框定成只能看、不能动
这个视图被标注为“3D 检视”。对于把渲染图当作组装参照的搭建者来说，没有任何对所看见内容采取行动的路径——没有标签来辨认设备，没有深度读数，也没有一个干净的画面可以拿来与实体机架对照。

上图场景取自当前应用真实的 3D 渲染（实时截取），拟议的界面元素叠加其上——你看到的是设计方案落在真实机架上的样子，而不是重新绘制的近似图。

D1
相机预设停靠栏
正面 / 背面 / ISO / 顶部，外加自动旋转，位于底部居中。SmoothCameraRig 已经实现了过渡动画——预设只是给它配上按钮。OrbitControls 保留为自由视角的兜底方式。
为何更优：隐藏的手势变成可发现的控件；“带我回到正面”是一下点击，而不是一顿瞎猜的拖拽。
D2
悬停提示 + 标签开关
悬停设备即浮出名称、U 位跨度、深度和功率；标签开关可为所有设备常驻显示。识别设备不再需要盲点。
为何更优：识别先于选择——不用先错开三个检查器面板，就能找到那台 NAS。
D3
深度检查卡片让承诺落地
检查器面板新增深度卡片：设备深度与机架的 railMinDepthMm–railMaxDepthMm 导轨区间对照绘制，并计算后部余量。数据早已在布局模型中，只是从未暴露。
为何更优：深度的组织方式恰恰是 2D 无法呈现的——这张卡片把它变成数值，于是你按毫米而不是按目测来排布。
D4
加载与恢复过程可见
懒加载 3D 代码块加载期间显示加载骨架屏 + 进度芯片；CanvasWithRecovery 在上下文丢失后重建场景时显示提示条。机制都已存在，只是此前一直静默。
为何更优：860KB 的懒加载代码块和 GPU 恢复若没有界面反馈，读起来就像“坏了”——有了状态提示才会让人觉得“在干活”。
D5
同一外壳、同一健康状态条，外加性能逃生舱
画布头部承载与 2D/线缆视图相同的健康芯片，各视图间的状态完全一致。性能模式（位于溢出菜单中）在弱 GPU 上关闭端口级几何体和标签。
为何更优：处处同一外壳意味着每个视图都无需重新学习；性能模式让大布局在集成显卡上也能用。
D6
线缆图层——设备与路由同处一个空间视图
线缆开关把路由路径（CableViewer3D 样条曲线）叠加到设备场景上，把现有的两座 3D 孤岛合二为一。你能同时看到 UPS、NAS以及它们之间真实的线缆松弛量——机架在物理上将成为的样子。
为何更优：走线占“实际看起来如何”的一半；把它藏在单独的模式里，等于让 3D 视图因遗漏而说谎。
D7
在 3D 视图中工作——并拿它与实体机架对照
选中、标签页式检查器面板和移动操作在 3D 中行为完全一致，因此整理工作（把设备挪一个 U 位、重新查看深度卡片）就发生在空间后果可见的地方。照片模式剥离所有界面框架，输出干净的渲染图，组装时可与真实机架对照。
为何更优：这个视图从“检视”升级为搭建者的参照——在其中整理，再用它核验实体搭建。
